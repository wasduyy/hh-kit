# hh-kit 战略思考

> 这不是一份营销文档。这是 hh-kit 设计过程中的真实认知记录——包括困惑、分歧、推翻和校准。

---

## 为什么做 hh-kit

### 痛点

AI IDE 的记忆层对用户不可见。对话长了，AI 开始"失忆"——忘了之前定好的技术选型、忘了项目约定、忘了上周做过的决策。用户只能感知到结果变差了，但看不到原因。

同时，大量想用 AI 做软件的人，不了解软件开发的基本流程（需求→分析→决策→任务→实现→验证）。他们跟 AI 说"帮我做一个 XX"，AI 就开始写代码——写到一半发现方向错了，改了，又错了，又改。

### hh-kit 做了什么

一套约定 + 工具，让 AI Agent 在写代码的同时自动维护工程过程记录：

- **追溯链**：需求→分析→决策→任务→实现→测试→缺陷→修复，每一步都有因果关联
- **会话记忆**：跨会话恢复上下文，不用每次从头解释
- **行为约束**：AI 不许擅自重构、不许铺张功能、改动必须有追溯
- **门禁检查**：推进阶段前验证完整性

## 诚实的问题

### 这些能力会被 AI IDE 吸收吗？

**会。一部分已经在被吸收。**

| 能力 | 当前状态 |
|------|---------|
| 会话记忆 | CLAUDE.md、Cursor memory、Trae rules 已经在做 |
| 编码规则注入 | 已经是 AI IDE 的标配 |
| 需求→实现关联 | GitHub Copilot Workspace 已经在做 |
| 追溯链 | 目前没有主流 IDE 在做 |

**hh-kit 是一个临时补丁**，填补 AI IDE 当前能力的缺口。当 IDE 原生支持过程记忆和追溯时，hh-kit 的核心价值会被吸收。

### 会被现有管理工具替代吗？

Jira/Linear/GitLab 都在做 AI 转型。他们有用户基础、分发渠道、品牌信任。当他们开始做"AI 编程过程追溯"时，会用自己的格式和协议。他们不需要 hh-kit。

### 为什么要做？

1. **现在有价值** — 当前 AI IDE 的记忆层确实不够用，hh-kit 填补真实缺口
2. **验证了思路** — 用完整开发案例跑通了全流程，证明"AI 编程过程可追溯"是可行的
3. **社区参考** — 即使最终被吸收，过程中的思考和实现可以作为社区的知识资产

## 定位的演变

hh-kit 的定位在开发过程中经历了多次校准：

### 阶段 1：工程纪律工具

> "让 AI 编程从补全工具升级为可管控的工程伙伴"

面向专业开发者，卖点是追溯链和门禁检查。但这个定位太窄——专业开发者有 Jira、有 CI/CD、有 code review 流程，不一定需要 hh-kit。

### 阶段 2：用户侧记忆增强器

> "让用户能控制 AI 记住什么"

面向非专业开发者，卖点是"不用每次从头解释"。这个定位更贴近真实痛点，但有一个问题——"零门槛"是伪命题。

### 阶段 3（当前）：诚实定位

用 AI 做软件和学习做软件是一回事。你不可能在不理解基本流程的情况下有效地使用 AI 来构建软件——就像你不可能在不了解经营环节的情况下有效地经营一家企业。

hh-kit 不是"让不懂软件的人也能用 AI 做软件"的工具。它是"让愿意学习的人，在实际操作中学会软件工程流程"的脚手架。

**关键认知**：
- 诚实的建议（"你需要学流程"）不能直接帮用户提升认知
- 用户必须自己踩坑、付出真实成本（token 费用、时间、方向偏差），才能理解流程的价值
- hh-kit 的作用不是避免踩坑，而是让踩坑**有据可查**——追溯链记录了每一步，回溯时能找到原因

## 关于 AI 编程的根本矛盾

### 用户认知 vs 实际成本

```
用户期望：AI 写代码 = 我不用学任何东西
实际成本：token 消耗 × 反复修改 × 方向偏差 × 不可维护
结果：花了很多钱，得到一个"能跑但改不动"的东西
```

### LLM 的偷懒问题

LLM 在推理时会选择更简单、低质量的回复来节省能量消耗。这导致：

```
用户不懂 → 给出模糊指令
  → LLM 偷懒 → 选择简单但低质量的实现
    → 用户不懂 → 无法发现质量问题
      → 继续给模糊指令 → 恶性循环
```

hh-kit 不能打破这个循环（只有用户认知提升才能打破），但能让循环的每一步都有记录。

### Token 经济的现实

Token 成本不会无限趋近于零。能源危机、LLM 公司的运营模式、推理成本都指向 token 经济。这意味着"用 AI 反复试错"是有真实成本的——而 hh-kit 的追溯和门禁能减少这种浪费。

## 来自第三方评审的校准

hh-kit 经过第三方 LLM 的四轮评审。评审中最有价值的发现是一个系统性偏差：

> **用传统软件工程标准评估 AI 工具，会产生大量误判。**

典型误判：

| 传统视角的批评 | 实际情况 |
|--------------|---------|
| "人类编辑 Markdown 会被覆盖" | 人类不编辑，AI 通过 MCP 操作 |
| "追溯链信息密度太高" | AI 不怕信息多，怕信息丢失 |
| "没有 pytest = 没有验证" | MCP 工具内建自验证 + 端到端验证 |

但传统视角也有正确的地方——状态语义不一致、缺少回归测试、文档残留。这些是真实的实现问题。

**结论**：不能完全用传统标准衡量 AI 工具，也不能忽视传统工程中经过验证的实践。hh-kit 试图在两者之间找平衡。

## 未来方向

### 短期（v0.2）

- 统一状态语义（done/completed/accepted）
- 增强 harness.summary.md 的可读性
- Skills 引用 defaults 减少冗余

### 中期

- 探索"用户可控记忆"的更好交互形式
- 降低 MCP 配置门槛（一键脚本）
- 观察主流 AI IDE 的记忆层演进，评估 hh-kit 的缺口是否在缩小

### 长期

hh-kit 最可能的终局是被 AI IDE 的原生能力吸收。但在吸收之前，它提供的价值是真实的——**让 AI 编程过程有据可查、有迹可循、有规可守。**

如果 hh-kit 的思想和实践能影响哪怕一个 AI IDE 厂商在设计记忆层时多想一步"用户需要看到什么"，那它的存在就有价值。
