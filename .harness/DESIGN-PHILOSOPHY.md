# hh-kit 设计理念问答

> 写给想理解"为什么 hh-kit 是这样设计的"的人类读者

---

## 关于名称

**hh-kit** = **Harness Helper Kit**。

harness（马具/安全带）在这里隐喻"工程驾驭层"——给 AI Agent 套上工程纪律的缰绳，让它在自由奔跑的同时不会偏离轨道。kit（工具包）强调轻量、即取即用。合在一起：**一套帮助 harness 管理工程过程的轻量工具包**。

---

## 致谢

hh-kit 的核心编码原则（Think Before Coding / Simplicity First / Surgical Changes / Goal-Driven Execution）改编自 **Karpathy-Inspired Claude Code Guidelines**。这些原则以 AI 行为约束指令的形式，存放在项目中的以下位置：

```
.harness/.scaffold/defaults/coding-principles.md
```

每当 AI Agent 开始工作时，这些原则会作为基础行为准则注入其上下文。

## Q1: hh-kit 到底是什么？

**一个给 AI Agent 用的工程纪律脚手架——同时也是给用户的项目过程记忆器。**

AI 写代码很快，但"为什么这么写"、"上次为什么选了 A 方案而不是 B"、"这个需求改了几次"——这些上下文每个会话都丢失。hh-kit 让 AI 在写代码的同时，自动维护一条**可追溯的因果链**，把"做了什么"和"为什么这么做"持久化下来。

对用户而言，hh-kit 解决的是 AI IDE 记忆层不可见的问题——你随时能看到 AI 记住了什么、做了什么决策、当前进度如何。

**核心隐喻**：人类是甲方，AI 是工程师，hh-kit 是给 AI 工程师配的项目管理系统，同时给甲方提供透明的过程视图。

---

## Q2: 为什么不直接用文档？为什么要 SQLite 追溯图？

文档是人写的，而 vibe coding 场景下**人不应该写文档**。

追溯链不是文档系统，是**有向图数据库**。AI 通过 MCP 工具创建节点和边，用递归 CTE 做上下游查询。这意味着：

- "这个实现追溯哪个决策？"——AI 在毫秒内回答
- "这个需求的所有下游实现有哪些？"——一次查询
- "追溯链有没有断裂？"——自动检测

Markdown 文件存在 `knowledge/` 下，但它们是 DB 的**只读投影**，不是人类手动维护的文档。

---

## Q3: "约定大于配置"具体指什么？

受 SpringBoot 启发。三个层次：

```
框架默认值    →  不配就能用
Starter 模板  →  选一个起点
项目覆盖      →  在 harness.yml 中显式声明偏离
```

典型例子：阶段模型。默认 5 个阶段（scaffold → implement → verify → integrate → acceptance），你不需要配任何东西就走这个流程。想改？在 `harness.yml` 里覆盖。

---

## Q4: 人类需要手动编辑 knowledge/ 下的 Markdown 文件吗？

**不需要。** 这是第三方评审中产生的一个典型误解。

在 vibe coding 场景下，所有追溯操作都由 AI 通过 MCP 工具完成。人类的工作流是：

```
你："我要做一个恒星渲染页面"
AI：创建 REQ 节点、分析节点、决策节点

你："开始实施"
AI：创建任务、实现节点、写代码、提交

你："收工"
AI：session-end，同步所有状态
```

你不会去手动改 Markdown 的 status 字段——你要改状态，跟 AI 说就行。

---

## Q5: 阶段模型是强制的吗？会不会限制迭代灵活性？

**不是强制的，是约定。**

`state_advance` 有 `skip_gate` 参数可以跳过门禁。`gate_check` 中 `tasks_completion` 是 info 级别，不阻塞。核心设计意图是**给 AI Agent 提供决策框架**——AI 在推进阶段前先检查"需求都实现了吗？追溯链完整吗？"，然后把结果汇报给你，你决定是否推进。

不是流程枷锁，是 AI 的决策参考。

---

## Q6: 追溯链会不会太重？每个小决策都要创建节点？

对人类来说重，对 AI 来说不重。

创建一个追溯节点 = 一次 MCP 调用，AI 的执行成本接近零。真正的问题是**AI 是否会自觉执行**——这正是 Skills 要解决的。Skills 定义了 AI 在特定场景下的行为 SOP，比如 research-and-plan Skill 会在研究阶段自动创建 ANA 和 DEC 节点。

---

## Q7: 为什么用文件系统 + SQLite，而不是更"现代"的方案？

**简单性优先。**

- 文件系统：零依赖、人类可读、Git 可追踪
- SQLite：零配置、单文件、递归 CTE 支持图查询

向量化知识库、Web 看板、Docker 化——这些是未来的优化方向（Layer 2/3），不是 Layer 0/1 的需求。hh-kit 的分层设计允许你从零依赖开始，逐步增强。

```
Layer 0: Git + AI IDE          → 完整可用（手动 Markdown）
Layer 1: + Python + SQLite     → 自动追溯、门禁
Layer 2: + Docker              → 团队协作（未来）
Layer 3: + 企业 ALM            → 大规模管理（未来）
```

---

## Q8: hh-kit 的 MCP Server 没有测试，可信吗？

**有验证，只是不是传统意义上的 pytest。**

hh-kit 的 MCP 工具是**自验证的**——每次调用都返回结构化的成功/失败结果。在实际开发中，我们用完整的开发案例（恒星生命周期 → 行星系统）跑通了全流程：35 个追溯节点、8 个 Skills 验证、门禁检查、状态同步。还通过 code-review Skill 发现了一个真实的 bug。

这比写一堆 mock 的单元测试更能证明系统在真实场景下能用。当然，未来会增加轻量的回归测试，但它不是第一优先级。

---

## Q9: 四区分离（.harness / .control / knowledge / project）的意义是什么？

让 AI 明确知道什么可以改、什么应该读、什么通常不改：

| 区域 | 职责 | AI 的操作权限 |
|------|------|-------------|
| `.harness/` | 框架内核 | 通常只读 |
| `.control/` | 运行时状态 | 读写（通过工具） |
| `knowledge/` | 过程资产 | 读写（通过工具） |
| `project/` | 开发产物 | 自由读写 |

这降低了 AI 误操作的风险——它不会"顺手"去改框架代码。

---

## Q10: hh-kit 最核心的一条设计原则是什么？

**AI 是操作者，人类是决策者。**

这条原则贯穿所有设计选择：
- 追溯链是给 AI 的运行时知识图谱，不是给人翻的文档
- Skills 是 AI 的行为 SOP，不是人的操作手册
- MCP 工具是 AI 的 API 层，不是人的 GUI
- 状态同步是 AI 自动执行的，不是人手动维护的

**人类只做三件事：描述需求、审批方案、审查结果。** 其余全部由 AI 驱动。

---

## 来自评审的认知校准

hh-kit 曾经过第三方 LLM 的四轮评审。评审中最有价值的不是"哪些地方做得好"，而是一个**系统性偏差的发现**：

> 用传统软件工程的标准评估 AI 工具，会产生大量误判。

典型误判模式：

| 传统视角的批评 | AI 视角下的真相 |
|--------------|---------------|
| "人类编辑 Markdown 会被覆盖" | 人类不编辑，AI 通过 MCP 操作 |
| "追溯链信息密度太高" | AI 不怕信息多，怕信息丢失 |
| "阶段模型限制灵活性" | 是 AI 的决策框架，不是人的流程枷锁 |
| "没有 pytest = 没有验证" | MCP 工具内建自验证 + 端到端验证 |

这个认知偏差是双向的：既不能完全用传统标准衡量 AI 工具，也不能忽视传统工程中经过时间验证的实践（比如状态机、配置管理、门禁检查）。hh-kit 的设计试图在这两者之间找到平衡——**用传统工程的管理思想，适配 AI Agent 的操作模式**。
